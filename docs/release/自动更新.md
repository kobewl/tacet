# 自动更新（发版与排障）

本文说明 Tacet 的应用内自动更新是怎么工作的、怎么发一个版本、以及出问题时去哪里看。

面向两类场景：**发版的人**（第二部分）和**排查更新问题的人**（第四部分）。

---

## 一、这套东西是什么，以及它做不到什么

Tacet 是**未做 Apple 代码签名与公证**的个人测试包，通过 GitHub Releases 分发。
应用内更新走的是 Tauri 更新器自己的 **minisign** 链路 —— 它与 Apple 签名是两条独立的事：

| | Apple 代码签名 / 公证 | Tauri 更新签名（本方案） |
| --- | --- | --- |
| 验证的是什么 | 应用的身份（谁做的这个 app） | 更新包有没有被篡改 |
| 需要什么 | 付费的开发者账号 | 一对本地生成的密钥（免费） |
| 当前有没有 | ❌ 没有 | ✅ 有 |

所以这套方案**能**保证：下载到的更新包确实来自本项目的发布，中途被替换的包装不进来。

它**不能**：

- 消除第一次打开未签名应用时的 Gatekeeper 提示；
- 保证「辅助功能」「通知」这类系统权限跨更新保留；
- 让安装过程完全无感。

那三件事都需要稳定的 Apple Developer ID 签名（通常还要配合公证）。
将来如果买了开发者账号，**可以保留现在这把更新密钥**，额外加上 Apple 签名即可 ——
两者不冲突，也不需要重新发布一次应用。

## 二、发一个版本

### 1. 升版本号（三处必须同时改）

| 文件 | 字段 |
| --- | --- |
| 根目录 `Cargo.toml` | `[workspace.package] version` |
| `apps/desktop/tauri.conf.json` | `version` |
| `packages/ui/package.json` | `version` |

这三处的一致性由两道检查守着：CI 的「红线 3」每次推送都查，
发布工作流在构建前还会再查一次，并额外核对**与 tag 一致**。

> **为什么必须与 tag 一致**：客户端读 `latest.json` 里的版本号跟自己的比，
> 只有更高才会认为「有更新」。如果 tag 是 v0.2.0 而应用版本还是 0.1.0，
> 这个版本就永远推不到用户那里 —— 而 Release 页面上它看起来一切正常。
> 这种「发布了但没人能更新」的状态最难查，所以在发版前就拦掉。

### 2. 测试

```bash
cargo test --workspace
pnpm --filter @tacet/ui lint
```

发布工作流也会跑 `cargo test`，但本地先过一遍省时间。

### 3. 提交并推送

```bash
git add -A && git commit -m "..." && git push
```

### 4. 打标签并推送 —— 这一步才会触发发布

```bash
git tag -a v0.2.0 -m "Release v0.2.0"
git push origin v0.2.0
```

标签推送后，`.github/workflows/release.yml` 会：

1. 核对版本号与 tag；
2. 构建前端产物；
3. 跑测试；
4. 构建**通用包**（同时支持 Apple 芯片与 Intel）并签名；
5. 创建 Release 并上传产物；
6. **核对产物与签名**（见下一节）。

### 5. 确认产物齐全

```bash
gh release view v0.2.0 --repo kobewl/tacet
```

应该看到这些附件：

| 附件 | 用途 |
| --- | --- |
| `Tacet_0.2.0_universal.dmg` | 手动安装（新用户） |
| `Tacet.app.tar.gz` | 自动更新下载的包 |
| `Tacet.app.tar.gz.sig` | 该包的签名 |
| `latest.json` | 更新清单，客户端读它发现新版本 |

工作流最后一步会自动检查这三样（`.app.tar.gz`、`.sig`、`latest.json`）在不在，
并**验证签名与内置公钥配对**。任何一项不满足，工作流会失败 —— 不要忽略它。

### 6. 验证清单能读到

```bash
curl -fsSL https://github.com/kobewl/tacet/releases/latest/download/latest.json \
  | jq '.version, (.platforms | keys)'
```

应输出发布版本号与 `darwin-aarch64`、`darwin-x86_64` 等平台键。

### 7. 在旧版本里实测一次

这一步不能省：**自动更新是一条只有真跑一次才能确认的链路**。

1. 打开一个较旧的 Tacet；
2. 菜单栏图标 → 设置… → 「关于」一节里的「检查更新」；
3. 确认它报出新版本号；
4. 点「立即更新」，看进度跑到 100%；
5. 应用自动重启后，确认设置页里的版本号已经变了。

## 三、密钥在哪里，以及一条不能做的事

| 东西 | 位置 | 是否保密 |
| --- | --- | --- |
| 私钥 | GitHub Secret `TAURI_SIGNING_PRIVATE_KEY` + 开发机 `~/.tauri/tacet-updater.key` | **保密**，且要离线备份 |
| 私钥密码 | 未设置（生成时留空） | — |
| 公钥 | `apps/desktop/tauri.conf.json` 的 `plugins.updater.pubkey` | 公开（随应用分发） |

生成密钥的方式（**已经做过了，不要重复执行**）：

```bash
npx tauri signer generate ~/.tauri/tacet-updater.key -p ""
```

> ### ⚠️ 不要轮换密钥
>
> 一旦有用户装了带某把公钥的版本，你**必须**用配对的私钥签后续所有版本。
> 换一把新密钥意味着：老用户无法验证新版本的签名，更新会直接失败，
> 而且**没有远程补救手段** —— 他们只能手动重新下载安装。
>
> 私钥丢了就等于更新链路断了。请离线备份 `~/.tauri/tacet-updater.key`。

每个应用应该用独立的密钥。Tacet 的密钥与 ClipMaster-Pro 的密钥是**两把不同的密钥**，
不要混用（发布工作流会用 key_id 比对来拦住这种混淆）。

## 四、出问题时

### 「还查不到发布信息」（检查更新时报这句）

这句来自 `update.rs` 对插件错误的翻译，原始错误是
`Could not fetch a valid release JSON from the remote`。

按顺序检查：

1. 仓库**发过** Release 吗？（`gh release list --repo kobewl/tacet`）
2. 最新这次 Release 里有 `latest.json` 吗？
3. `latest.json` 里有当前平台的条目吗（Apple 芯片是 `darwin-aarch64`）？
4. 应用里的 `endpoints` 地址与实际 Release 下载地址一致吗？

第 2 条最常见。它通常是因为 `tauri.conf.json` 里漏了
`bundle.createUpdaterArtifacts: true` —— 没开这个就不会产出 `.sig` 和 `latest.json`。

### 构建报「A public key has been found, but no private key」

原文：

```
A public key has been found, but no private key.
Make sure to set `TAURI_SIGNING_PRIVATE_KEY` environment variable.
```

这句话出现在打包**之后**，所以日志里会先看到一串正常的 `Bundling` 输出，
最后才失败 —— 容易误判成「打包坏了」。

它真正的意思是：`tauri.conf.json` 里配了公钥（说明要产更新包），
但这次构建没提供私钥。

- 在**发布**环境：Secret `TAURI_SIGNING_PRIVATE_KEY` 没配，或名字拼错了。
- 在 **CI / 本地**（本来就不该签名）：加 `--config '{"bundle":{"createUpdaterArtifacts":false}}'`
  来关掉更新产物。CI 的 `build-app` job 就是这么做的。

> 注意：`TAURI_SIGNING_PRIVATE_KEY` 要的是**密钥文件的内容**，不是路径。
> 官方文档提到的 `TAURI_SIGNING_PRIVATE_KEY_PATH` 在 2.x 的 CLI 上不被识别
> （实测过），只设它一样会报这个错。

### 报「签名不匹配」/ 运行时报签名验证失败

发布用的私钥不是应用内公钥的配对私钥。**不要重新生成密钥对**，
而应该找回最初发布那把公钥时用的私钥。

发布工作流里的 `compare-signature-key.py` 就是拦这个的：
它比对签名与公钥里共同的 `key_id`。如果它失败了，说明 Secret 配错了密钥。

### 已经发出去的版本缺更新文件

**不要移动已发布的 tag**。修好配置后，发一个新的补丁版本（例如从 v0.2.0 到 v0.2.1）。
老版本会自然检测到更高的版本号，审计记录也更清楚。

如果只是想重跑工作流（配置问题，产物还没被人下载过），可以：

```bash
gh workflow run release.yml --repo kobewl/tacet -f tag=v0.2.0
```

## 五、设计取舍：为什么更新是手动触发的

Tacet 没有「启动时自动检查更新」。这是有意的：

- 一个常驻菜单栏的健康工具在后台偷偷联网，是一件需要向用户解释的事；
- 产品原则 7 是「不配置任何东西时它也该安静地工作」；
- 更新检查会发一次网络请求，而用户对「谁在什么时候联网」应当有知情权。

所以 v0.1 里更新**只在用户点「检查更新」时**发生。
将来如果要做后台检查，它也应该是一个**默认关闭**的开关。

## 附：开机自启（同一节设置里的另一个开关）

开机自启与自动更新是两件独立的事，但都住在设置页里，且都会被
「换了台机器 / 重装了系统」影响，所以放在一起说明。

### 状态存在系统里，不在数据库里

真正的开关是 `~/Library/LaunchAgents/Tacet.plist`。设置页每次打开都
**直接问系统**，不缓存 —— 用户可以随时在「系统设置 → 通用 → 登录项」里
把它改掉，缓存一份就会显示过期状态。

想手动确认当前状态：

```bash
ls ~/Library/LaunchAgents/ | grep -i tacet
```

有 `Tacet.plist` 就是开着的，没有就是关着的。

### 为什么用写 plist 而不是 SMAppService

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 写 LaunchAgents plist（当前） | 对**未签名**应用也能用 | 应用被删掉后 plist 会残留 |
| `SMAppService`（macOS 13+） | 系统代管，卸载时自动清理 | 对未签名应用有兼容风险 |

Tacet 目前没有 Apple 证书，所以选了前者。将来完成签名后，**这一处应该升级到
`SMAppService`** —— 库层已经为此留好了位置（`crates/platform-macos/src/startup.rs`
的模块注释里写了怎么换）。

### 关闭自启后应用仍会自启？那是另一条路径

macOS 有一个独立于登录项的机制：关机时还在运行的应用，下次登录会被系统
恢复。Tacet 是常驻菜单栏的工具，关机时多半开着 —— 也就是说它可能**从这条
路径自己回来**。

代码里已经在 `RunEvent::Ready` 调用 `disableRelaunchOnLogin` 关掉了它。
如果你发现「关掉开关后应用仍然自启」，先确认这一点是否生效：

```bash
grep -A2 "开机自启" ~/Library/Application\ Support/Tacet/logs/tacet.log
```

日志里没有「disableRelaunchOnLogin 必须在主线程调用，已跳过」这句，
就说明它生效了。

### 开发版不能设置自启

`tauri dev` / `cargo build` 编出来的是 debug 版，设置开关会报错并说明原因。
这不是 bug：开发版需要本地的开发服务器才能显示界面，注册成登录项后
开机只会留下一个点开是空白的菜单栏图标。要测这个功能，请用正式打包的版本。
